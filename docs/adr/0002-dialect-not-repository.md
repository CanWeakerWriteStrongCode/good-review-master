# 0002 不为换库抽 Repository 接口，只把方言差异收在一处

- 状态：已采纳
- 日期：2026-11-04
- 影响范围：`state` 包全部读写

## 背景

有人提过"以后可能要上 MySQL"（多实例、集中备份）。按教科书做法，这时候应该抽出 `Repository` 接口、给 SQLite 和 MySQL 各写一套实现。评估时统计了一下实际的库代码：

| 项 | 数量 |
| --- | --- |
| `state` 包非测试代码 | 2305 行 |
| 其中真正跟 SQLite 绑定的（DDL、裸 SQL、PRAGMA、upsert 语法） | 299 行 |
| 表 | 12 张 |

也就是说，真要换库，要动的是那 299 行和几条方言，而不是 2305 行。抽一层接口的收益对不上它的成本。

## 决策

不引入 `Repository` 接口，也不做双实现。所有 SQL 只出现在 `state` 包里，其他包看到的是 `Scope` 上的方法（`SaveMessage`、`LoadRecent`、`Messages`……）。

库特有的东西集中在三处：

1. `schema.go` —— DDL、索引、触发器、`PRAGMA user_version`。
2. 少数裸 SQL —— `ON CONFLICT`、`AUTOINCREMENT`、`strftime`、`MAX()` 这类。
3. `Open` 里的连接参数 —— WAL、单连接。

换库时改这三处，加上把 12 张表的 DDL 翻译一遍；业务代码一行不动，因为它们本来就不碰 SQL。

## 后果

- 少了一层接口定义和两套实现，也就没有"接口为了兼容两端而长得又宽又空"的问题。
- 表结构、查询、事务的写法可以按 SQLite 的最优方式来，不用迁就两个数据库的交集。
- 代价：换库不是改配置就能完成的事，得改 `state` 包内部；也没有"同一份测试跑两个数据库"这种保障。
- 另一个代价：SQLite 的特性会渗到查询里（比如自增号的行为、WAL 的读写并发语义），后来的人如果按 MySQL 的直觉改，容易踩坑。这也是为什么写入规则要单独写一篇 ADR。

## 被否的方案

- **`Repository` 接口 + 双实现**：每条查询写两遍、测试跑两套，而当前只有一种库在用。等真有第二个库时再抽，抽取成本不会比现在更高（SQL 已经集中）。
- **完全交给 GORM 自动迁移**：建表结果不可控，索引和触发器的表达力也不够。本项目需要精确控制自增、唯一键和触发器，所以 DDL 手写。
- **现在就换 MySQL**：单机单进程、数据量在百 MB 级，换来的只是多一个要运维的服务。
