# 0005 各域由编排层用消息串联，不引消息队列

- 状态：已采纳
- 日期：2026-11-04
- 影响范围：`pipeline`、`bot`、`workspace`、`assets`、`speech`、`config` 的 `pipeline` 段

## 背景

系统里有几个职责完全不同、成本和失败方式也完全不同的域：

| 域 | 典型耗时 | 失败方式 |
| --- | --- | --- |
| 补成员名 + 入库 | 毫秒 | 库忙、锁等待 |
| 图片描述 | 几百毫秒到几秒 | 视觉模型超时、限流 |
| 生成回复 | 十几秒到几十秒 | 模型超时、工具调用卡住 |
| 管理指令 | 毫秒到一秒 | 副作用不能重放 |

早期是在 HTTP 处理器里一路同步调完。问题是 AstrBot 那边有超时，处理一慢它就重推同一条消息；重推又触发一轮模型调用，越堵越多。

另一个问题是域之间的调用关系。如果 `speech` 直接调 `assets` 打标签、`bot` 直接调 `workspace` 入库，那「一条消息先经过谁、再经过谁」就散落在每个调用点上；加一个域要回头改所有上游，也没法按会话串行、没法背压。

还有一个顺序要求：同一个群的消息必须按到达顺序处理（否则上下文会乱），不同群之间则应该并行（否则一个活跃群拖住所有群）。

## 决策

1. **域之间不互相调用，由编排层驱动**。编排层是 `bot` 包里的 `orchestrator`：它按消息决定这条消息先交给哪个域、再交给哪个域，域只从自己的入口被调用，不反向调别的域。
2. **域之间只走消息**。每次交接就是一次 `pipeline.Item` 编码（`Body` 是 JSON 载荷），放进 `pipeline.Buffer`；域本身不知道上游是谁，也不知道下游是谁。
3. **一个域一段消费**。每段是一个 `pipeline.Stage`：固定大小协程池 + 每会话串行。协程不绑定会话，从就绪队列挑一个 `key` 处理一批，交还后再挑下一个；`inflight` 标记保证同一个 `key` 同一时刻只有一个协程持有。
4. **阶段数是编排层的配置，不是架构约束**。域与域之间的连线是一张表（`orchestrator` 的 `nodes` / `workflows`），加一个域 = `mount` 一次 + `connect` 一条，其它域不动。今天是一个前置 + 两条工作流，改成三条同样不需要动已有域。
5. **数据平面与控制平面分开**。管理指令走自己的 Stage，不占打标签与生成的并发槽，也不进群聊缓存。
6. **队列满时 `Put` 阻塞**（由 ctx 控制），不静默丢。入站那一层最多等 2 秒，等不到就回 503 让 AstrBot 知道。
7. **阶段之间只传能序列化的值**，不传 `*Workspace` 这类运行时指针。`Item.ID`（`stage|tag|key|消息ID`）天然是幂等键。
8. **参数现读**。批量、凑批等待、并发、重试放在 `StageConfig`，每批读一次，改 `settings` 表不用重启。
9. **终止是链的属性，不是域的动作**。域交回的是「这一步发生了什么」，交完就结束，不表达「我是最后一站」。还走不走，看这条工作流声明过的 `ends`（到此为止）和 `next`（下一站是谁）。好处是同一个域能挂在多条工作流上复用：一条可以让它执行完继续去审计，另一条声明它到此为止，域一行代码不改。
10. **入口与补名是工作流之外的前置**。所有消息都要过补名（补昵称、补引用、写库），但它不做业务——把它放进任何一条工作流，那条工作流就成了「共享节点」，加工作流时要回头改它。所以它单独挂（`mountRouter`），只回一句「走哪条工作流」；工作流用 `workflow` 声明、之间互不相连。
11. **工作流是消息的 tag，域是消息的 topic**。`Item` 带两级身份：`Stage` 是目标域（接 MQ 时是 topic，谁消费），`Tag` 是所属工作流（接 MQ 时是 tag，属于哪条链）。前置只回工作流名，`dispatch` 把它记成 tag；之后每一跳都带着，去向只在本工作流的 `next` / `ends` 里查。这层是照 RocketMQ 的 topic + tag 模型设计的：加一条工作流只加一个 tag 值，不建 topic、不复制消费组配置；两条工作流可以各有一个 `done`；同一个域也能被多条工作流复用，消息不会串线。

## 后果

- 慢的下游只影响自己那一段：图片描述卡住时，补名入库照常在跑，回复队列照常排队。
- 加域是加法，不是改造：新域只需要实现一个处理函数，在编排层 `mount` 一次、`connect` 一条。
- 池大小就是并发上限，跟群数量无关。一百个群和一千个群用同样多的协程。
- 一个协程连续吃同一会话最多 3 批就让位（`maxBurstPerTurn`），避免活跃群把池子占死。
- 进程崩溃时内存里的存量消息会丢。**但正文不丢**：补全那一段是同步入库的，重启后从库里恢复最近消息，丢的只是"还没生成回复"这个动作。
- 只能单机跑：换第二个实例时两个进程各有一份队列，同一个群的消息会被两个进程并行处理，顺序就没了。要横向扩展就得把 `Buffer` 换成真正的 MQ。
- 代价：`pipeline` 里多了一层"就绪队列 + inflight + 条件变量"的调度代码，比 `go func()` 复杂。这部分用 `worker_test.go` 覆盖。
- 一个域能被多条工作流复用：同一个处理函数，在哪条继续、在哪条终止，由那条工作流的拓扑决定；消息自带 tag，复用同一个域也不会串线。
- 代价：终点必须逐条手写（`orch.exit`）。漏写不会静默生效，会在 `dispatch` 里报“既没连线也没声明终点”，也能用测试覆盖。“没连线”因此保留了它的原义：装配错误。
- 以后要不要真上 MQ、换之前缺什么，以及当时的实测与测算：[design/](../design/)。

## 被否的方案

- **HTTP 处理器里同步调完所有域**：就是被换掉的方案。AstrBot 超时重推，越堵越多。
- **域之间直接互相调用**（`speech` 直接找 `assets` 要标签、`bot` 直接调 `workspace` 入库）：处理顺序被硬编码在每个调用点，加一个域要改所有上游；跨域的失败重试、按会话串行、背压都没有统一落点。
- **把管理指令留在补全那一段里就地执行**：控制平面会跟数据平面抢同一个并发槽，指令卡住会连累消息入库；指令失败也不该重试。
- **`go func()` + `WaitGroup`，无队列**：没有背压——高峰期协程数无限增长，最后 OOM 而不是变慢。
- **每个群一个常驻 goroutine**：顺序天然满足，但群数就是协程数；几百个群时调度开销和内存都不划算。
- **Redis / RabbitMQ**：能解决跨进程和持久化，但当前是单机单进程，多一套中间件就要多一套部署、监控、故障处理。接口已经按"可换 MQ"设计（`Buffer` 是接口、载荷是 JSON、`Item.ID` 是幂等键），等真要多实例时再换。
- **把"到此为止"写进域里**（域返回空就表示结束）：单链时看不出问题，因为"链的终点"和"域的终点"恰好重合。多条链时同一个域不可能对一条链沉默、对另一条链说话——要让它继续就得改域，两个需求只能满足一个。
