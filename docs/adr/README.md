# 决策记录

一个决策一个文件，编号递增，写下去就不再改。判断错了就新写一篇，把旧的标成"已被取代"。

## 什么时候该写

- 有两个以上说得通的选项，并且别人可能会问"为什么不选那个"。
- 这个选择有代价，且代价是刻意接受的。
- 改动会影响后续多个模块的写法。

不值得写的：改名、拆文件、调参数、修 bug。

## 格式

30~60 行，五段，不要更多：

```md
# NNNN 一句话说清做了什么决定

- 状态：已采纳 | 已被 ADR-XXXX 取代 | 已废弃
- 日期：2026-11-04
- 影响范围：涉及哪些包或模块

## 背景

什么情况下要做这个决定。带上真实数字和触发它的事实，不要写"为了提升质量"。

## 决策

具体做了什么。能写成规则就写成规则。

## 后果

得到了什么、付出了什么。代价要写清楚，别只写好处。

## 被否的方案

每个方案一句：它解决了什么、为什么不够。
```

## 状态怎么变

- **已采纳**：现在是这么做的。
- **已被取代**：新决策推翻了它。正文不动，只改状态和链接，让后来的人能看到当时的理由。
- **已废弃**：当时对，现在这块功能没了。
