# 0003 建库只建最新版，不做旧库升级链

- 状态：已采纳
- 日期：2026-11-04
- 影响范围：`state/schema.go`、启动流程、发布说明

## 背景

`state/schema.go` 里原来有一条从 v1 到 v16 的升级链。它不只是"加个列"：里面有 4 处一次性数据搬运，跑完就该删但一直留着——

| 版本 | 那段代码干的事 | 删掉会怎样 |
| --- | --- | --- |
| v6 | 把旧 `meta` 表透视成 `workspace_profile` | 老库启动后画像为空 |
| v11 | 回填 `groups` 的消息数与最后时间 | 面板所有群计数归零 |
| v11 | 保证 v12 要用的列存在 | 老库直接 `no such column` |
| v12 | 把身份表并进群档案 | 老库丢了账号与群的对应关系 |
| v15 | 给各表补自增主键 | 老库的 `id` 不是自增，后续写入报错 |

这些东西的共同点：**只会跑一次，但永远不能删**——因为一旦还有 v5 的库，删了就崩。于是每次改表都要在两处写代码（新结构 + 从旧结构搬过来），还要各配一个测试。当时 12 个升级测试里有 10 个是在测这些搬运。

前提变了：现在还在开发阶段，数据全是测试数据，没有生产库，也没有测试服。

## 决策

1. `schemaVersion` 取当前最新值（具体数字随改表上涨，只在 `state/schema.go` 写一处），`migrate` 只有一条路：**把空库建成最新结构**。
2. 闸门比"版本号等于 0"更严一点：`user_version > 0` **或者** 库里已经有 `messages` 表，都算旧库，直接报错并提示删文件。
3. 旧库没有"原地升级"，也没有"自动备份再迁移"。删掉 `state.db`、`-shm`、`-wal`，重启就是新库。

第 2 条里那个"或者已有 `messages` 表"是必要的：`CREATE TABLE IF NOT EXISTS` 遇到一个有表但没有版本号的库会一声不响地跳过，最后得到一个缺列却写着最新版本号的库，错误会推迟到运行时才爆。

## 后果

- `schema.go` 删掉了 12 个辅助函数（`ensureColumn`、`rebuildTableWithID`、`mergeIdentitiesIntoGroups` 等）和 12 个升级测试，只剩建表 DDL。
- 建表 DDL 成了结构的唯一真相。想知道表长什么样，只看一个文件的一处。
- 代价：**每次改表都要清库**。开发时无所谓，将来如果有真实部署，升级会变成"导出、删库、重启、导入"的人工步骤，必须写进发布说明。
- 代价：再也不能说"我兼容旧版本"。遇到旧库只能让用户删文件，这需要产品上接受。

## 被否的方案

- **保留升级链，只删那几处 upsert**：删掉 backfill，老库会被判成"已是最新版"却缺数据，症状是面板计数全 0——比报错更难查。
- **保留升级链，加最低版本闸门（只支持 v16 以上）**：还是个链子，下次改表照样要写搬运代码，只是把问题推迟。而 v16 以前的库已经没有价值。
- **换 golang-migrate / Flyway 这类工具**：它们解决的是"多版本、多环境、可回滚"的迁移管理。当前的问题不是工具不够，而是根本不需要支持旧库；引入工具只会多一套文件和一列版本表。
