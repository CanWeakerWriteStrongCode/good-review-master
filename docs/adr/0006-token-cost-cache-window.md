# 0006 缓存窗口按 token 成本决定扩展还是重置，不按固定条数

- 状态：已采纳
- 日期：2026-11-04
- 影响范围：`conversation`（缓存与锚点）、`speech/generate.go`、`config` 的 `llm` 段

## 背景

请求是无状态的，省钱全靠服务端的前缀缓存：把上次发送的那段原样再带上，命中的部分按命中价计费。命中价与未命中价差得很远——按当时的价目表约 1:30，所以参数取 `cache_hit_cost = 0.033`、`cache_miss_cost = 1.0`。

早期用固定条数决定带多少：环形缓冲 200 条，每次带 `llm_send_count`（20）条重置窗口，或者从锚点扩展到 200 条。

两个问题：

1. 群聊消息长短差十倍。20 条可能是 200 token，也可能是 4000 token，条数根本不对应成本。
2. 模型或价格一变，那个 200 就没有依据了。扩大观察到的现象是"明明配了缓存，账单还是很高"，缩小则是"上下文被截断，模型答非所问"。

## 决策

每次发送前，在两种做法里按成本算一次：

| 做法 | 带什么 | 成本估算 |
| --- | --- | --- |
| 扩展 | 锚点位置到最新（含上次发送的全部内容） | 旧前缀 × `cache_hit_cost` + 新增 × `cache_miss_cost` |
| 重置 | 最近 `llm_send_count` 条 | 全部 × `cache_miss_cost` |

规则：

1. 有锚点、且锚点没超过 `cache_ttl_sec`、且扩展后总量不超 `max_context_tokens`，才算扩展的成本。
2. 扩展更便宜就扩展，否则重置。
3. `cache_ttl_sec`（默认 900 秒）故意取偏小：把还在的缓存当成没了，代价只是多发 20 条；反过来是几万 token 全价。
4. `max_context_tokens`（默认 12000）是硬护栏，只约束 system + 工具清单 + 聊天记录；工具结果、回传图片、user 固定尾巴不在护栏内（那部分长度不可控，硬算会把正常请求也拒掉）。

## 后果

- 群聊密集时前缀一直热，多数请求走扩展，账单里命中部分占大头。
- `cache_hit_cost` 必须明显小于 `cache_miss_cost`。两个值接近时扩展永远算不过重置，窗口每次从头重算，缓存形同虚设——这是配置上最容易犯的错。
- 锚点是每个工作空间一份内存态，重启后第一次必然重置。这是可接受的：冷启动只多花一次全价。
- 决策结果和命中量都有指标（`llm_window_mode_total`、`llm_cache_hit_total`），可以对照账单验证参数是否合理。
- 代价：多了一层成本估算，读代码时要同时看 `cache_ttl_sec`、`max_context_tokens`、两个单价才能说清"这次为什么重置"。

## 被否的方案

- **固定条数**：就是被换掉的方案。条数不等于 token，且阈值会随模型和价格失效。
- **永远带全量上下文**：前缀命中率最高，但会撞上下文上限；一旦超了被拒或截断，整轮对话就废了。
- **永远重置，不带历史**：实现最简单、成本可预测，但每次都是全价，且模型看不到上下文，回复质量明显下降。
- **按字符数/字节数算**：比条数准，但仍与 tokenizer 不成比例（中文、代码、表情的 token/字符比差很多）；项目里保留字符数估算只用于粗算和日志，不用于选窗决策。
