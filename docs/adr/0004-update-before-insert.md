# 0004 单行写入先 UPDATE，没命中才 INSERT

- 状态：已采纳
- 日期：2026-11-04
- 影响范围：`state/messages.go`、`state/directory.go`、`state/schema.go` 里的群统计触发器

## 背景

`messages` 的主键是 `id INTEGER PRIMARY KEY AUTOINCREMENT`，唯一键是 `(workspace_id, group_id, message_id)`。`id` 不只是主键，它还是发给模型看的消息编号——"第 37 条"指的是这个号，跨窗口、跨重启都不能变。

同一条消息会被写不止一次：

1. 入站时先落一行（占住编号，保证顺序）。
2. 补齐成员名、补上被引用消息时回填一次。
3. 图片打完标签，把 `image_ids` 写回去。

原来用的是 `INSERT ... ON CONFLICT DO UPDATE`。问题出在 SQLite 的实现顺序：**冲突检测之前就先分配了 rowid**。所以一次"其实只是更新"的写入，也会让 `AUTOINCREMENT` 的计数器往前走一格。三次写入 = 烧三个号，消息编号变成 1、4、7……，模型看到的"第 37 条"和面板显示的对不上。

## 决策

规则一句话：**先用唯一键 UPDATE，`RowsAffected == 0` 才 INSERT。**

| 情况 | 实际执行 | 消耗的自增号 |
| --- | --- | --- |
| 命中（补名回填、图片回填） | 一次 `UPDATE` | 0 |
| 未命中（新消息） | `UPDATE` 返回 0 → `INSERT` | 1 |

群统计的两个触发器照同一个思路写：先 `UPDATE groups ...`，`WHERE NOT EXISTS` 时才 `INSERT`。否则每次群里有动静都会给 `groups` 白烧一个号。

配套前提是**单写连接**（见 [ADR-0001](0001-single-shared-db.md)）：UPDATE 返回 0 到 INSERT 之间不会有另一个写入插队，所以不需要事务或重试。如果以后改成多写连接，这段要加事务，否则两个协程可能都拿到 0 再各插一行。

## 后果

- 自增号只在真正新增一条消息时消耗，面板上的编号连续，模型引用不会错位。
- 命中时是 1 次往返（原来的 upsert 也是 1 次），未命中时是 2 次。回填的场景远多于新插入，所以总体往返次数没变。
- 写入路径不再依赖 `ON CONFLICT` 语法，换库时少一处方言。
- 代价：这条规则必须靠人守。新写一个 upsert 很容易又退回去，所以三个"不白烧号"的测试要在每次改动后跑：群统计、其余表、单行写入各一个。

## 被否的方案

- **`INSERT ... ON CONFLICT DO UPDATE`**：就是被替换掉的方案。语义最直观，但会白烧号，而这号是对外的编号。
- **`REPLACE INTO`**：语法最短，但它是"删了再插"——rowid 会变，`AUTOINCREMENT` 照样前进，还会触发删除侧的级联与触发器。
- **先 `SELECT` 判断存在再决定**：多一次查询，且 SELECT 与写入之间有窗口期（虽然单连接下不会真的并发，但读放大是实打实的）。
- **改用业务 ID 当主键、不要自增号**：模型看到的编号会变成一长串 ID，既不好引用也不稳定（QQ 的 `message_id` 在某些实现里换群就变）。
