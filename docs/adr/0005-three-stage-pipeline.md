# 0005 三阶段流水线 + 内存缓冲，不引消息队列

- 状态：已采纳
- 日期：2026-11-04
- 影响范围：`pipeline`、`bot`、`config` 的 `pipeline` 段

## 背景

一条群消息要走三段成本完全不同的处理：

| 段 | 典型耗时 | 失败方式 |
| --- | --- | --- |
| 补成员名 + 入库 | 毫秒 | 库忙、锁等待 |
| 图片描述 | 几百毫秒到几秒 | 视觉模型超时、限流 |
| 生成回复 | 十几秒到几十秒 | 模型超时、工具调用卡住 |

早期是在 HTTP 处理器里一路同步走完。问题是 AstrBot 那边有超时，处理一慢它就重推同一条消息；重推又触发一轮模型调用，越堵越多。

把三段拆开之后还有一个顺序要求：同一个群的消息必须按到达顺序处理（否则上下文会乱），不同群之间则应该并行（否则一个活跃群拖住所有群）。

## 决策

1. 三段各一个消费者（`pipeline.Stage`），中间用两条内存队列 `B2`、`B3`（入站还有 `B1`）。
2. **协程不绑定会话**：池里固定 N 个协程，从就绪队列里挑一个 key 处理一批，交还后再挑下一个。`inflight` 标记保证同一个 key 同一时刻只有一个协程持有；不同 key 并行。
3. 队列满时 `Put` **阻塞**（由 ctx 控制），不静默丢。入站那一层最多等 2 秒，等不到就回 503 让 AstrBot 知道。
4. 阶段之间只传 `pipeline.Item`，`Body` 是 JSON。不传 `*Workspace` 这类指针。
5. 参数（批量、凑批等待、并发、重试）放在 `StageConfig`，每批现读，改 `settings` 表不用重启。

## 后果

- 慢的下游只影响自己那个阶段：图片描述卡住时，补名入库照常在跑，回复队列照常排队。
- 池大小就是并发上限，跟群数量无关。一百个群和一千个群用同样多的协程。
- 一个协程连续吃同一会话最多 3 批就让位（`maxBurstPerTurn`），避免活跃群把池子占死。
- 进程崩溃时内存里的存量消息会丢。**但正文不丢**：Stage 1 是同步入库的，重启后从库里恢复最近消息，丢的只是"还没生成回复"这个动作。
- 只能单机跑：换第二个实例时两个进程各有一份队列，同一个群的消息会被两个进程并行处理，顺序就没了。要横向扩展就得把 `Buffer` 换成真正的 MQ。
- 代价：`pipeline` 里多了一层"就绪队列 + inflight + 条件变量"的调度代码，比 `go func()` 复杂。这部分用 `worker_test.go` 覆盖。

## 被否的方案

- **HTTP 处理器里同步处理**：就是被换掉的方案。AstrBot 超时重推，越堵越多。
- **`go func()` + `WaitGroup`，无队列**：没有背压——高峰期协程数无限增长，最后 OOM 而不是变慢。
- **每个群一个常驻 goroutine**：顺序天然满足，但群数就是协程数；几百个群时调度开销和内存都不划算。
- **Redis / RabbitMQ**：能解决跨进程和持久化，但当前是单机单进程，多一套中间件就要多一套部署、监控、故障处理。接口已经按"可换 MQ"设计（`Buffer` 是接口、载荷是 JSON、`Item.ID` 是幂等键），等真要多实例时再换。
