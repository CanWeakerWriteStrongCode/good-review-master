# 0001 所有账号共用一份 state.db，按 workspace_id 分区

- 状态：已采纳
- 日期：2026-11-04
- 影响范围：`state`、`workspace`、`web/server`、备份流程

## 背景

最初只有一个机器人账号，库就是一个 `state.db`。要接第二个号时，最直接的想法是"一个号一个库文件"，但接着就出现几件麻烦事：

- 面板要同时展示两个号的数据。两个库意味着跨文件查询或者应用层归并，"全部会话"这种视图做不出来。
- 备份要拷 N 份文件，主备切换要把另一个库整个换过来。
- 两张表之间的关联（比如某个成员在两个号眼里的两个 openid）跨库就没法 join。

## 决策

一个文件装所有账号的数据，每张业务表都带 `workspace_id` 列，联合唯一键的第一段就是它。

读写一律走 `state.Scope`：构造时绑定一个 `workspace_id`，之后所有方法都不用再传，也就不会漏过滤条件。唯一不带过滤的是面板的跨账号视图和启动时的恢复扫描。

## 后果

好的一面：

- 面板一个查询就能列出所有账号的群与会话。
- 备份、迁移、重建都只有一个文件（加 `-shm` / `-wal`）。
- 主备两个号在同一个物理群里可以各自维护缓存，数据互不影响，切换只是换配置。

代价：

- **写是全局串行的**。SQLite 的写锁是库级的，所以进程只开一个写连接。一个号在批量入库时，另一个号的写入要排队。现在单机单进程，这个量级可以接受；真到了写不动的规模，办法是换存储而不是拆库。
- 所有查询都必须记得带 `workspace_id`。这一条靠 `Scope` 强制执行，不靠人自觉。
- 库损坏时是全部账号一起坏。缓解办法是定期 `VACUUM INTO` 一份副本。

## 被否的方案

- **一个账号一个库文件**：面板聚合、备份、跨账号关联都要额外写代码，换来的是"写可以并行"——而当前的单写连接本来就不是瓶颈。
- **一个账号一个进程**：进程内不用再区分工作空间，代码最简单；但每个进程都要连模型、连 MCP、跑一份流水线，部署和资源成本翻倍，且面板要跨进程聚合。
- **换 PostgreSQL / MySQL 再谈多账号**：为还没出现的规模引入运维负担，且失去"单文件可拷走"这个部署优势。
