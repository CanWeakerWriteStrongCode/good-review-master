# 2026-11 缓存成本测算

> 状态：Implemented
> 日期：2026-11
> 结论落在：[ADR-0006](../adr/0006-token-cost-cache-window.md)

一次记录，不是规范。用来给 `llm` 段的几个参数找依据；换模型或调价后要重算。

## 问题

无状态请求 + 前缀缓存。每次回复前要决定带多少历史：

- **扩展**：从上次的锚点开始，把上次发过的全部内容原样再带上，再追加新消息。
- **重置**：丢掉锚点，只带最近 `llm_send_count` 条。

两种做法的成本差多少，划算的边界在哪。

## 记号

| 记号 | 含义 | 取值 |
| --- | --- | --- |
| `W` | 已经在缓存里的消息条数 | 200 |
| `P` | 本次新增条数 | 20（= `llm_send_count`） |
| `avgTok` | 每条平均 token（中文按 1 字 ≈ 1 token 高估） | 20 |
| `H` | 命中单价（相对值） | 0.033 |
| `M` | 未命中单价（相对值） | 1.0 |

token 估算：中文实际约 1 token 吃 1.5 个字，按 1 字 1 token 算是**上限**，所以下面的成本偏保守。

## 单次成本

```
扩展            = W × avgTok × H + P × avgTok × M
重置(保同上下文) = (W + P) × avgTok × M
重置(只带最近P条) = P × avgTok × M
```

## 算一遍

| 做法 | 实际带多少历史 | 成本（折成全价 token 当量） |
| --- | --- | --- |
| 扩展 | 220 条 ≈ 4400 token | 200×20×0.033 = 132，加上 20×20×1 = 400 → **532** |
| 重置，但保住同样 220 条上下文 | 220 条 | (200+20)×20×1 = **4400** |
| 重置，只带最近 20 条 | 20 条 ≈ 400 token | 20×20×1 = **400** |

三个数放在一起能看出两件事：

1. **在"保住同样上下文"的前提下，扩展便宜约 8 倍。** 这就是前缀缓存的意义：4400 → 532。
2. **但"只带 20 条"只要 400，比扩展还便宜一点**，代价是模型只能看到最近 20 条。所以"省钱"和"保上下文"是两笔账，不能混着说。

也就是说：扩展不是因为它比"重置到 20 条"便宜，而是因为它用 1.3 倍的价钱换 11 倍的上下文。值不值取决于话题跨度——跨了几百条的话题，扩展是对的；各聊各的，重置更划算。

## 真正的硬约束不是成本

`max_context_tokens`（12000）才是。4400 token 的窗口加上 system prompt、工具清单、固定尾巴，离 12000 还有余地；但窗口再涨一倍就到了。到那时候不是"划不划算"的问题，是请求会被拒或者被截断。

所以顺序是：先看会不会超护栏，再看成本。

## 什么时候扩展不划算

| 情况 | 为什么 |
| --- | --- |
| 锚点超过 `cache_ttl_sec`（900 秒） | 服务端的 KV 缓存多半已经被挤掉。这时 `W` 实际按 `M` 计费，扩展 = 4400 + 400，比直接重置还贵 |
| `cache_hit_cost` 配得接近 `cache_miss_cost` | 扩展省下的那部分趋近于 0，永远算不过重置，缓存形同虚设 |
| 消息长度分布极不均（一条长截图、几百条"哈哈哈"） | 按条数 × 平均值估出来的数会偏得很厉害，这也是选窗要按 token 而不是按条数的原因 |

## 平均消息长度与缓存容量

`max_cache_msg`（200）只决定内存里留多少条，不影响成本——成本由"这次带几条"决定。粗算：200 条 × 20 token ≈ 4000 token 的文本，加上结构开销，每个群几百 KB 量级。几十个群也就几十 MB，不构成压力。

缓存条数要大于窗口可能的最大长度，否则"想扩展却发现历史已经被环形缓冲挤掉了"，只能被动重置。

## 落到的配置

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `cache_hit_cost` / `cache_miss_cost` | 0.033 / 1.0 | 当时的价目表约 1:30；换模型必须重算 |
| `cache_ttl_sec` | 900 | 偏小取值：把还在的缓存当成没了，代价是多发 20 条；反过来是几万 token 全价 |
| `max_context_tokens` | 12000 | 本地 llama-server `-np 4` 时每槽 8192 真实 token，按 1.6 倍高估换算 |
| `llm_send_count` | 20 | 重置时带多少条 |
| `max_cache_msg` | 200 | 环形缓冲上限，要大于窗口最大长度 |

## 局限

- 按"条数 × 平均长度"估算，不看真实分布；真实用量看 `llm_tokens_total` 和 `llm_cache_hit_total`。
- 没把 system prompt、工具清单算进去，那部分每轮固定，不随窗口变化，但不小。
- 单价是假定值。换了模型或上游调价，这张表要重算——更可靠的做法是对着账单看 `llm_cost_total{workspace}` 和 `llm_window_mode_total` 的比例。
